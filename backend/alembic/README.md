# Alembic migrations

`synchronize=False` is permanent for this app's `OrmModule.for_root_async(...)` (see
`src/app_module.py`) -- schema creation/evolution is owned entirely by the migrations in
`alembic/versions/`, not by boot-time `CREATE TABLE` sync. (Unit/e2e tests are the one deliberate
exception: they build their own disposable in-memory SQLite `DataSource` with
`synchronize=True` for speed/no-live-DB -- that's test-only and unrelated to this rule.)

## Hard rule: every entity ships with a migration, in the same change

`alembic/env.py`'s `target_metadata` is built from `src.db.entities.ALL_ENTITIES` -- the single
list both `AppModule` (the running app) and this migration tooling import, so they can never
silently drift apart. That means:

- **Adding a new entity?** Add it to `ALL_ENTITIES` in `src/db/entities.py`, then generate a
  migration in the *same* unit of work (see commands below). Don't let the entity list and the
  migration history drift apart, even temporarily within one session.
- **Adding/changing a column on an existing entity** (e.g. Phase 1.10's `User.status`/`is_active`
  addition) that lands in the same session as that entity's *initial* migration? Fold the column
  into that same migration file rather than generating two migrations for the same table in one
  session -- keep the history clean.
- This applies to every phase from here on (Phase 2's `kyc` module, Phase 3's `issuance`, Phase
  4's `holdings`, etc.) -- not just Phase 1.

## Commands

Run from `backend/` with `DATABASE_URL` pointed at a real (or locally Dockerized) Postgres --
autogenerate needs a live connection to diff against:

```bash
# generate a new migration from the current ALL_ENTITIES vs. the DB's current schema
uv run alembic revision --autogenerate -m "<short description>"

# apply all pending migrations
uv run alembic upgrade head

# roll back one migration
uv run alembic downgrade -1
```

Always review an autogenerated migration before committing it -- Alembic's Postgres/`ENUM`
autogenerate has a known limitation where `downgrade()` never emits `DROP TYPE` for named enum
columns (see `versions/60429c1b1184_initial_schema.py`'s `downgrade()` for the manual fix-up
pattern to copy for any future enum column).
